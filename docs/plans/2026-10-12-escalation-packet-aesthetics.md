# Escalation packet aesthetics: rendered chat, terminal-friendly layout, packet viewer

Status: FINAL, 4 units (epa-1..epa-4). Part 4 (epa-4) was a placeholder until
2026-10-12, when the user chose Approach C from the Fable design review. Fast
path: 4 dispatchable units, so no task-master and no `to-tickets`.

## Goal

When a unit escalates (ESCALATE-TO-HUMAN), the human should be able to read
the escalation packet's `CHANGES.md` and `EXAMPLES.md` quickly:

1. **Rendered in chat.** The orchestrator puts the files' contents in its own
   message text, outside any code fence, so Claude Code renders the markdown.
   Today they arrive as an unrendered Read tool result, with raw `###`,
   backticks and `1.` visible. The verbatim / in-full rule, the no-summary
   rule, and the never-author-or-extend-EXAMPLES rule all stay as they are
   (epa-1).
2. **Laid out for a terminal reader.** The reviewer writes short lines. In
   `## What to look at first` it writes a `>` blockquote callout followed by a
   `| Where | What to check |` table. Each example in `EXAMPLES.md` gets a
   heading plus `**Before:**` / `**After:**` lines. The content rules do not
   change (epa-2).
3. **Packet viewer.** Every packet carries a `view.sh` that renders the two
   files in colour in the human's own terminal. It tries `glow`, then
   `bat`/`batcat`, then `rich`, and falls back to plain `cat`, so it works with
   none of them installed. The orchestrator prints the command and never runs
   it (epa-3).
4. **Marker card (Approach C).** Line 1 of the `.escalated` marker is
   byte-unchanged. Below it, the body becomes a six-line card (why /
   would-be verdict / look first / decide / run / packet), a `---` fold
   line, then the record. The orchestrator prints only lines 1 through the
   fold, plus one pointer line (epa-4).

Out of scope: the Microworld dashboard, the DECISION / `AskUserQuestion` flow,
and anything the reviewer *decides*.

### Design decisions (self-resolved; see Clarifications)

- **D1 — How chat rendering is produced.** The orchestrator Reads the file,
  then reproduces the contents as its own message text. It drops the Read
  tool's `N<TAB>` line-number prefixes and uses no code fence. A tool result
  on its own does not count as "printing". The existing in-chat display of
  the `.escalated` marker (step 1) is unchanged; part 4 owns the marker.
- **D2 — Viewer location and authorship.** The reviewer writes `view.sh` into
  `.claude/human-review/<task-id>/` in the same action as `PACKET.md`,
  `CHANGES.md` and `EXAMPLES.md`. It goes into **every** packet, with or
  without a bundle, because `CHANGES.md` always exists. It is written
  **after** the bundle copy, so it replaces any bundle file of the same name.
  It is copied byte-for-byte from a canonical block embedded in the four
  instruction sources, then `chmod +x`.
  - It is not a plugin-shipped file: a codex/cursor reviewer has no plugin
    path, and a new installed file would add a cli.js file spec and
    fileHashes.
  - Byte-identity of all copies is enforced by a new test. That test also
    executes the block.
- **D3 — How the command is surfaced.** The `.escalated` marker body is **not**
  changed in parts 1-3. The packet path is always
  `.claude/human-review/<task-id>/`, so the orchestrator prints
  `sh .claude/human-review/<task-id>/view.sh` next to the marker's `run.sh`
  command when that file exists. Using `sh …` means a lost executable bit
  cannot break it. (Superseded by epa-4: the card's `packet:` line now
  carries the command.)
- **D4 — Fallback order.**
  1. `glow <file>`
  2. `bat --paging=never -l md <file>`
  3. `batcat --paging=never -l md <file>` (the Debian/Ubuntu name)
  4. `rich --markdown <file>`
  5. `cat <file>`

  A renderer that is present but exits non-zero falls through to the next
  one. The script always exits 0. It is POSIX `sh`, ASCII only, read-only,
  and contains neither `DECISION` nor `human-review`.
- **D5 — Layout scope.**
  - Tables appear only in `## What to look at first`, as one `file:line` per
    row. They are not used per Walkthrough subsection, which would bloat the
    file beyond the 120-line soft cap.
  - One `>` blockquote line opens that section and names the single place to
    look first.
  - The words "no new tool, no rendering, no HTML" are replaced with "plain
    markdown, no HTML": the packet now has a viewer, so the old words would
    contradict epa-3.

### Canonical packet viewer block (D2/D4; byte-exact, copied into four sources by epa-3)

The block goes at column 0, not indented under a list item. It is delimited
by the two HTML comment lines, with a ```` ```sh ```` fence inside them:

````
<!-- view.sh:begin -->
```sh
#!/bin/sh
# Escalation packet viewer: renders CHANGES.md and EXAMPLES.md in colour when
# glow, bat or rich is installed, else prints them plain. Read-only.
dir=$(cd "$(dirname "$0")" && pwd)
for f in CHANGES.md EXAMPLES.md; do
  p="$dir/$f"
  [ -f "$p" ] || continue
  if command -v glow >/dev/null 2>&1 && glow "$p"; then :
  elif command -v bat >/dev/null 2>&1 && bat --paging=never -l md "$p"; then :
  elif command -v batcat >/dev/null 2>&1 && batcat --paging=never -l md "$p"; then :
  elif command -v rich >/dev/null 2>&1 && rich --markdown "$p"; then :
  else cat "$p"
  fi
done
exit 0
```
<!-- view.sh:end -->
````

## Risks / dependencies

- **R1 — The units are strictly sequential:** epa-1, then epa-2, then epa-3.
  Each edits overlapping files and takes the next patch version. The
  expected versions are 0.31.156, 0.31.157 and 0.31.158, but criteria never
  pin a number: re-derive it from `.claude-plugin/plugin.json` at execution
  time.
- **R2 — Probe wrapping.** Parity probes use `String.includes` on raw text,
  so each new probe string must sit on one physical line in both ports
  (examples-2 history).
- **R3 — Mirror trap.** The `.claude/agents/*.md`, `.claude/persona-protocol.md`
  and `.claude/persona-config.json` fileHashes are generated. Hand-editing
  them is a P2 violation (packet-brevity-1 history).
- **R4 — Dashboard tables render as pipe text.** This is deferred, see Open
  Question 1. Resolved 2026-10-13 by epf-4 (table support in markdown-lite.js).
- **R5 — The orchestrator may still paste inside a fence.** epa-1 changes
  instructions only, and no test can observe live orchestrator output. The
  criteria pin the instruction text, not the runtime behaviour.
- **R6 — epa-4 reshapes the `.escalated` body below line 1.** epa-3 adds no
  marker line, so the two units do not conflict beyond their shared files.
  The machine readers parse line 1 only (`decisions.js:37`, `server.js:346`,
  `human-decision-gate.sh:232-234`); this was measured and is guarded by
  AC4.6 and AC4.7.
- **R7 — Dashboard display of the card.** `markdown-lite` renders the card
  in `PACKET.md` as plain lines with an `<hr>` at the fold. That is
  acceptable; the dashboard is out of scope.
