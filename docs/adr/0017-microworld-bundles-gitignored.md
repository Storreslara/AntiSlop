# ADR 0017: Microworld bundles are gitignored, not committed

Date: 2026-07-28
Status: Accepted (plan 2026-07-28-microworlds-ubiquitous-language-human-review, Step 8b)

## Context

Microworld bundles are working-session artifacts produced by `lead-programmer` during implementation: one bundle per unit, holding the canonical inputs, expected outputs, and `run.sh` check contract. They are consumed by the reviewer and re-executed reactively on every edit via the `PostToolUse` hook, so they must exist in the working tree throughout the session.

The question is: what happens to a bundle when the session ends? Does it survive across clones and process boundaries (committed), or is it working-tree scratch (gitignored)?

## Decision

**Microworld bundles are gitignored working-tree scratch, not committed.** This is the user's explicit override (2026-07-28, Open Question 3) of this plan's original recommendation to commit them. The override reasoning is correct and load-bearing:

- **Bundles encode session-relative artifacts** (test fixtures, expected outputs). Committing them couples project history to ephemeral working-state definitions.
- **Bundles are generated by agents**, not authored by humans. Reviewing bundle changes is reviewing agent output, not project decisions.
- **The cost of committing outweighs the benefit:** every bundle commit is a review noise point, and the bundle-as-source-of-truth assumption breaks the moment a human changes a fixture without re-running the bundle, or a test's expected output drifts from reality.

Gitignoring bundles is the sound choice.

## Accepted cost: the survivability gap

Gitignoring bundles creates a survivability problem that committing would have solved for free: a bundle exists only for the life of the working tree. If a unit escalates and a human is not available immediately, the bundle is gone by the time they return — `git clean -fdx`, a fresh clone, or a discarded worktree all destroy it.

This gap is **accepted, not fixed** by introducing durable escalation packets (`.claude/human-review/<task-id>/`). The two mechanisms together close the gap:

1. **The bundle is gitignored scratch** — no commit overhead, no review noise, no historical coupling.
2. **At escalation, a packet snapshots the bundle** — an untracked but persistent copy, deleted only when the reviewer resolves the escalation.
3. **The packet is marked in the `.escalated` marker** — commit SHA is recorded so a human arriving in a fresh clone can check out the commit and reproduce the state, even if the packet is gone.

This two-part design avoids committing bundles while preserving human reviewability.

## Rationale for overriding the original recommendation

**The original recommendation (commit bundles) was reasoned as follows:**
- Bundles are the canonical definition of a unit's verification contract.
- Committing them ensures they survive session and process boundaries.
- Code review of bundles is review of the agent's test strategy, which is valuable.

**This reasoning is correct but incomplete.** The cost it missed:

- **Review noise:** every bundle is a working artifact, changing on nearly every edit. Committing them means nearly every code review must wade through a bundle diff that is not a project decision — it is the reviewer re-verifying the agent's choice of test inputs.
- **Fixture staleness:** a human reviewer who changes an expected output without updating the bundle creates an inconsistency the review process cannot detect. The bundle-as-source-of-truth assumption collapses.
- **Coupling to ephemeral session state:** bundles encode outputs from a specific run at a specific commit. Committing them couples the project's history to "what the agent produced on Tuesday," which is not a project truth worth preserving.

The user's override to gitignore instead is the right call because it trades away the "free" survivability of committed bundles for a much cleaner burden: the bundle is scratch (no review noise, no historical coupling), and when human escalation needs a durable copy, the **escalation packet mechanism** explicitly handles that case.

## Consequences

### For the reviewer

The reviewer must **never assume a bundle exists from looking at the diff**. Bundles do not appear in `git diff` or `git status`. The reviewer establishes bundle presence by **looking at the filesystem** (`ls microworlds/<unit-slug>/`) — it is a second, independent check, not derived from the diff.

### For a human reviewing an escalated unit in a later session

The escalation packet (`.claude/human-review/<task-id>/`) is the runnable artifact. The working-tree bundle is long gone, but the packet survives as an untracked directory. If the packet is lost (e.g., `git clean -fdx` after a resolve), the packet and its marker are unrecoverable — the commit SHA in the `.escalated` marker lets a human check out that commit and re-review it.

### For CI and fresh clones

Fresh clones and CI runs never see bundles. The `PostToolUse` hook and all tests that depend on bundles are designed to no-op silently when `microworlds/` does not exist. This is the **normal** state, not an edge case.

## Limitations and open items

**R10 — escalation packets are clone-fragile (accepted).**
Packets are untracked, so `git clean -fdx`, a fresh clone, or a discarded worktree destroys a pending escalation unrecoverably, together with its evidence (the `.escalated` marker, also untracked). The only recovery is checking out the commit SHA recorded in the marker (if preserved in git log) and re-reviewing. This is accepted rather than fixed: the alternative is committing review scratch into project history, which is what the gitignore decision rules out.

**R5 — stale `.escalated` after `skip:` (pre-existing shape, not new).**
Writing `skip: <reason>` into a pending-review flag deletes the flag but not the marker file or packet. At the next reviewer `SubagentStop`, a stale `.escalated` glob would keep flags standing again. This hazard exists today, identically, for `.blocked` — the glob is by filename. It fails **safe** (over-blocks, never under-blocks) and clears when the reviewer next resolves that unit and deletes the marker. Documented as a known limitation, not fixed here.
